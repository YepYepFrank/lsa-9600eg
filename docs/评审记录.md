**验收**：`g0:verify` 24 / 24；后端 `sim:verify` 22 / 22、`e:verify` 18 / 18（AH03 由 EG 端采集时）。
链路：仿真器 → Mosquitto → IoT Gateway 3.8.5 → AH03 的 Edge → 子站 TB，子站看到的数据落后约 1 s，**设备侧时间戳原样保留（差 0 ms）**。

**实测发现**

1. **IoT Gateway 3.8.5 的 JSON 转换器 `"timeseries": ["*"]` 可以原样转发**，载荷是 `{"ts","values"}` 时保留设备时间戳。不用写 Python 转换器，key 带点（`ir.t_max`）也不受影响。
2. **EG 自己的数据不能走 IoT Gateway 的普通连接器**：把 `EG-AH03` 当子设备发时，Edge 立刻以「Normal disconnection」断开网关会话、5 s 后重连 —— 每发一次断一次。
   另开一条 MQTT 连接用同一令牌直发也不行：TB 一台设备只留一个会话，两条互相挤掉。
   解决：自写一个小连接器 `LsaSelfConnector`（Python，60 行），订阅 `lsa/EG-<柜号>/…`，经网关**自己的会话**发 `v1/devices/me/…`。自检里加了「发 EG 自身数据时会话没被断开」一项。
3. 因此 IoT Gateway 的普通连接器改为**按设备清单逐台订阅**（不用 `lsa/+/…`）：顺带挡住同事发错设备名时在 Edge 上建出野设备。
4. **AH03 交给 EG 端后，EG 设备本身没数据，子站会判它离线**（`sim:verify` 的「EG-AH03 active」失败、自监控报「Edge 卡住」）。所以 EG 自身指标提前在 G0 就发了（完整指标仍在 G1）。
   启示：现场如果 eg-agent 挂了，子站会对这面柜报「通信中断」，而实际数据还在上送 —— G1 要让 IoT Gateway 在 agent 停掉时也能维持 EG 在线（候选：LsaSelfConnector 自己每 30 s 补发一条 `eg.state`），待 G1 定。
5. Edge 上行断开后大约每 3 分钟重连一次：开发机上先起 EG 样机、后起子站模拟器（上行经它转发）时，最多要等 3 分钟数据才到子站。
6. 开发机上 IoT Gateway 每 60 s 检查一次配置文件，agent 启动时重写配置会让连接器重启一次（几秒），无害。
