**验收**：`g0:verify` 24 / 24；后端 `sim:verify` 22 / 22、`e:verify` 18 / 18（AH03 由 EG 端采集时）。
链路：仿真器 → Mosquitto → IoT Gateway 3.8.5 → AH03 的 Edge → 子站 TB，子站看到的数据落后约 1 s，**设备侧时间戳原样保留（差 0 ms）**。

**实测发现**

1. **IoT Gateway 3.8.5 的 JSON 转换器 `"timeseries": ["*"]` 可以原样转发**，载荷是 `{"ts","values"}` 时保留设备时间戳。不用写 Python 转换器，key 带点（`ir.t_max`）也不受影响。
2. **EG 自己的数据不能走 IoT Gateway 的普通连接器**：把 `EG-AH03` 当子设备发时，Edge 立刻以「Normal disconnection」断开网关会话、5 s 后重连 —— 每发一次断一次。
   另开一条 MQTT 连接用同一令牌直发也不行：TB 一台设备只留一个会话，两条互相挤掉。
   解决：自写一个小连接器 `LsaSelfConnector`（Python，60 行），订阅 `lsa/EG-<柜号>/…`，经网关**自己的会话**发 `v1/devices/me/…`。自检里加了「发 EG 自身数据时会话没被断开」一项。
3. 因此 IoT Gateway 的普通连接器改为**按设备清单逐台订阅**（不用 `lsa/+/…`）：顺带挡住同事发错设备名时在 Edge 上建出野设备。
4. **AH03 交给 EG 端后，EG 设备本身没数据，子站会判它离线**（`sim:verify` 的「EG-AH03 active」失败、自监控报「Edge 卡住」）。所以 EG 自身指标提前在 G0 就发了（完整指标仍在 G1）。
   启示：现场如果 eg-agent 挂了，子站会对这面柜报「通信中断」，而实际数据还在上送 —— G1 要让 IoT Gateway 在 agent 停掉时也能维持 EG 在线（候选：LsaSelfConnector 自己每 30 s 补发一条 `eg.state`），待 G1 定。
5. Edge 上行断开后大约每 3 分钟重连一次：开发机上先起 EG 样机、后起子站模拟器（上行经它转发）时，最多要等 3 分钟数据才到子站。
6. 开发机上 IoT Gateway 每 60 s 检查一次配置文件，agent 启动时重写配置会让连接器重启一次（几秒），无害。

| 实测 | 结果 |
|---|---|
| 负荷率 | 近 30 s 14 点逐点核对 = max(Ia,Ib,Ic) ÷ 72，时间戳与电流相同 |
| 单个量停发（env.t / env.rh） | 先 stale 后 invalid，子站 q 只标这两个量；恢复后 30 s 内回 "{}" |
| 整台停发（颗粒物） | 6 个量全 invalid、EG 降级、南向超时计数上涨；恢复后回到 online |
| 同事自发 q | 与看护结果合并，子站保留、不被冲掉；发 "{}" 清掉 |
| agent 停发 40 s | 12 s 后代发 degraded，子站始终判 EG 在线；agent 回来后 online |
| 重启 Mosquitto / IoT Gateway / 本柜 Edge | 7 s / 8 s / 43 s 恢复，**期间数据无断档**（最大间隔 2.0 s） |
| 断上行 2 分钟 | Edge 本地排队，恢复后 60 s 补齐，无断档 |
| 内存 | eg-agent 147 MB（Windows 宿主进程，Linux 容器里 G6 再测）、IoT Gateway 37 MB、Mosquitto 2–3 MB |

**实测发现**

1. IoT Gateway 默认的干净会话在它重启那几秒会丢同事发的数据；改持久会话后 Mosquitto 替它排着，重启 IoT Gateway 无断档。Mosquitto 默认每个客户端只排 1000 条（本柜约 10 分钟），调到 5 万条。
2. 本柜 Edge 重启（43 s）期间 IoT Gateway 自己的内存队列兜住了，无断档。
3. 开发机的时钟比 NTP 快 1.7 s（`w32tm` 独立测得 −1.70 s，与 SNTP 结果一致），子站网关页把 AH03 标「时间戳可疑」—— 是真实状况，不是缺陷。
4. 子站页面看到的几处与 EG 端无关、但交接后会暴露的问题，列在下面待确认 G1-1。
5. AH03 今天的曲线在交接后只有两处缺口（16:26、16:29 各十几秒），都是开发中手动重启仿真器（相当于同事的程序停了），不是链路丢数。

**实测发现**

1. **扩展服务的 JSON 解析会吃掉请求体**：反代挂在它后面时，经子站发给 EG 的 POST 到 EG 已是空体。改为关掉 Nest 自带解析、先挂反代再挂解析（`main.ts`），自检加了「经反代的 POST 请求体原样到达 EG」。
2. **Edge 上送偏移属性的更新时刻不能当「还在上送」**：Edge 攒一批才写一次，断网后它还显示刚更新过，初版把「断着」判成了「补传中」。改为 agent 每 5 s 自己采样、记偏移最后前进的时刻与速度。
3. 改本地口令会让其他本地会话作废（设计如此），自检初版在改完口令后还拿旧会话去测，后面一串 401 —— 是自检的问题，已改。
4. 模拟器让出 AH03 后不再给它生成录波 / 抓拍占位文件，子站 `b5:verify` 的「录波列表」跳过了。改为让出的柜也照生成，直到 G5 由 EG 真上传替换。顺带：模拟器的运行计划按全部柜排，供电链路上 T1 / AA01 的负荷率又跟回 AH03。
5. 访问令牌在配置页上原先回显前 3 位 + 后 2 位，改成只显示「已设置（20 位）」。

**LsaSelfConnector 重载死锁（I1 修复引入，I4 发现）**

- 现象：i4:verify 里「应用后 cfg 属性进本地 TB」失败。追下去：EG 自身的遥测与属性（eg.*、cfg、egAgentVersion）从 16:53:17 起一直进不了本地 TB；IoT Gateway 此后不再打任何日志。传感器数据走内置 MQTT 连接器自己的线程，照常进本地 TB，本地告警、i3 / i4 的其余各项都正常，所以不显眼。
- 原因：I1 的修法让新实例在 `open()` 里**拿着单实例表的锁**去调旧实例的 `close()`，而 `close()` 也要拿这把锁；`threading.Lock` 不可重入，同一线程自己把自己锁死。`open()` 是 IoT Gateway 主线程在重载连接器时调的，于是主线程卡住。16:53:17 那次重载是 agent 重启重写 IoT Gateway 配置触发的。（起先以为是 `loop_stop()` 等网络线程与 `gateway.send_*` 等主线程互等；改了那处仍复现，在容器里用两个实例复现后才定位到锁。那处也一并改成不等，免得真遇上。）
- 为什么 I1 当时没发现：i1:verify 的「连接器稳定」只在不重载的 2 分钟窗口里看 taken over 与 eg.state；I1 修复后网关刚重启过（单实例、无重载），自检跑完之后才发生第一次重载。I1 时日志里那句「上一个实例还在，先关掉它」后面其实再没有「订阅本机总线」，当时只看了 taken over 次数（新实例卡死自然是 0 次），没看出来。缺的是「重载本身」的回归项。
- 修法：`open()` 在锁里只登记、取出旧实例，**锁外**再关旧实例；锁改成 `RLock` 兜底；`close()` 不等任何线程（断开与 `loop_stop` 放后台线程），已停实例收到消息直接丢，看门线程见停即退。新实例用同一 clientId 连上时 Mosquitto 踢掉旧会话，旧客户端处于主动断开状态、不会重连。在容器里用两个实例（假网关、测试设备名）验证：第二个实例 `open()` 立即返回、新实例转发属性与遥测、旧实例已停。
- 回归：`i1:verify` 加 6b（常驻）：只改 `lsa_self.json` 的修改时间触发重载，查新实例订阅上、重载后 EG 自身指标与属性照常进本地 TB、之后不反复 taken over。

## §8.1 修订：上送单次发布 ≤ 48 KB（2026-09-27）

后端规模测试发现子站 TB 的 MQTT 单条消息上限 64 KB（tb-node `NETTY_MAX_PAYLOAD_SIZE` 缺省），超了直接断开连接；按「一次 ≤ 500 条」切的补传批 87–101 KB，被断、重连、重发同一批，永远补不完。EG 的 outbox 有同样风险（I2 时 AH03 单批小，没碰到）。
约定改为一次发布 ≤ 500 条**且 JSON 载荷 ≤ 48 KB**，子站不调大上限。

- 切批抽成纯函数 `apps/agent/src/uplink/chunk.ts`：按主题分组，按估算大小与条数分组，再按实际载荷核对、超了对半再分；单独一行就超 48 KB 的记审计（`uplink.oversized`）、记丢失段、从 outbox 删掉，不卡队列。
- `i2:verify` 加 0b 节（临时库）：一面柜 30 分钟积压 3903 条（含带谐波的电表、一条 70 KB 的畸形数据），假子站收到 > 64 KB 就「断开」—— 49 次发布补完、最大 47.0 KB、每次最多 108 条、畸形那条丢弃，4 / 4。
- 与 G4 一起，等联调时用户重启 agent 生效。
