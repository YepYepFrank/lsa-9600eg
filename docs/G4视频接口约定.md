# G4 视频接口约定（2026-09-27 协调会话审定，引为后端库《EG独立TB调整方案》§8.5）

> 2026-09-27。依据：开发计划 v0.4 §6.5、用户答复（每柜一台双目 ONVIF 摄像机、视频不经 TB、按需拉不全推）。
> 现状：子站视频通道是**每隔室（每台 SAM）一路**，路径 `<柜号>-<隔室字母>[-ir][-sub]`，模拟阶段由子站 mediamtx 的 ffmpeg 出测试画面。
> **2026-10-10 厂家答复（待确认事项清单 4.4 版 CAM1–CAM8）**：RTSP 端口固定 554、地址可用 restv1 `GET /restv1/channel/rtsp/:id` 查；默认 H.264（可选 H.265）；码率单位 kbps；**热像主码流 640×480**；抓拍 `GET /restv1/channel/snap/:id`（base64 JPG）；没有 ONVIF 事件、没有健康接口；最多 2 个会话同时连；出厂有默认账号口令，投运必须改（部署手册 §5a）。已写进 §5、§6、§9。
> **2026-10-14 真机实测**（开发网，restv1 接口）：四路分辨率 / 帧率、接口与 RTSP 是两套账号、出厂地址等见 **§10**。

## 1. 通道与路径：每柜一组、四路

| 路 | EG mediamtx 路径 | 子站 mediamtx 路径 | 用途 |
|---|---|---|---|
| 可见光主码流 | `<柜号>` | `<柜号>` | 单窗 |
| 可见光子码流 | `<柜号>-sub` | `<柜号>-sub` | 9 / 16 分屏 |
| 热像主码流 | `<柜号>-ir` | `<柜号>-ir` | 单窗 |
| 热像子码流 | `<柜号>-ir-sub` | `<柜号>-ir-sub` | 分屏 |

两级同名，排障时一眼对得上。柜号即 `tb/model.yaml` 的柜号（大写字母数字，如 `AH03`）。

## 2. 按需拉：两级 `sourceOnDemand`

> **2026-09-27 修订（G5，§8.7 §1）**：交接说明 §14.1 要求录像覆盖故障前，边缘不能「没人看就不拉」。所以 **EG 这一级两路子码流（`<柜号>-sub`、`<柜号>-ir-sub`）一直拉、一直录**（`sourceOnDemand: false`、`record: yes`）；两路主码流仍按需拉；子站 → EG 各路仍按需拉。下面按需拉的描述对主码流与子站那一级仍成立。

```
摄像机（LAN1）◀─RTSP─ EG mediamtx（:8554）◀─RTSP/TCP─ 子站 mediamtx ─WHEP / HLS─▶ 浏览器
```

- **EG mediamtx**（eg-video 按 `local.yaml` 生成 `config/mediamtx.yml`）：每路 `source: rtsp://<账号>:<口令>@<摄像机>/…`（地址来自 ONVIF 或手填，§5），`sourceOnDemand: yes`、`sourceOnDemandStartTimeout: 10s`、`sourceOnDemandCloseAfter: 10s`，`rtspTransport: tcp`。**没有读者就不连摄像机**（仅主码流；子码流见上方修订）。
- **子站 mediamtx**（后端按 `model.yaml` 生成）：每柜四路 `source: rtsp://<EG 上行 IP>:8554/<路径>`，`sourceOnDemand: yes`、`sourceOnDemandStartTimeout: 10s`、`sourceOnDemandCloseAfter: 10s`，`rtspTransport: tcp`（走 TCP，EG 防火墙只放 8554/TCP，不放 UDP 端口段）。EG 上行 IP 取 `EG-<柜号>` 的属性 `ipUp`。
- **时限**：浏览器关掉后，子站到 EG 的流 ≤ 10 s 断（EG 上行无视频流量）；EG 那一级再过 ≤ 10 s 断开摄像机的**主码流**。**摄像机侧没人看时也一直有两路子码流**（约 1 Mbit/s，循环录像用）。首帧：两级冷启动 + 摄像机建连，目标 < 3 s（G4 实测）。
- 开发环境：EG 样机的 mediamtx 与子站的在同一台机器上，EG 的 RTSP 用 **18554**（`local.yaml video.rtspPort`，现场缺省 8554）；子站 AH03 的四路 source 写 `rtsp://host.docker.internal:18554/<路径>`（后端给个开发覆盖，同 `EXT_EG_URLS` 的做法）。

## 3. EG 8554 只对子站开放

- 防火墙：EG 入站 8554/TCP 只放子站主机地址（部署手册 §1）。
- mediamtx 自身再限一道：`authInternalUsers` 只给 `sp.host`（解析成 IP）与 `127.0.0.1`（eg-video 抓帧）**读**权限，任何地址都不许推流、不开 WebRTC / HLS / API 对外（API 只听 127.0.0.1，给 eg-video 读状态）。

## 4. 摄像机指标：报在 `CAM-<柜号>`（已有的摄像机设备）

eg-video 每 60 s 发到本机总线 `lsa/CAM-<柜号>/telemetry`（与传感器数据同一条路：进本地 TB、由 agent 上送子站；点表目录里已有，周期 `minute`）：

| key | 含义 | 取法 |
|---|---|---|
| `cam.online` | 四路里能用的路数（0–4） | 每路对摄像机做一次 RTSP `DESCRIBE`（不拉流） |
| `cam.fps` | 可见光主码流帧率 | 该路正在被拉时取 mediamtx 实测；没人看时取 SDP 的 `a=framerate`；都没有就不报 |
| `cam.bitrate` | 四路入站码率之和（kbps） | mediamtx API 的入站字节数差；没人看时为 0 |

EG 自身（`EG-<柜号>`）不报 cam.*。摄像机整台连不上时 `cam.online=0`，并由 agent 的质量码看护照常标 `q`。

## 5. 流地址从哪来：ONVIF 为主，可手填

- `local.yaml camera.onvif` 给了设备服务地址（`http://<摄像机>/onvif/device_service`）与账号口令：eg-video 启动时及每 10 分钟调 ONVIF `GetProfiles` + `GetStreamUri`（WS-Security 摘要认证），按视频源分可见光 / 热像、按分辨率分主 / 子码流。
- `local.yaml camera.rtsp.visible / visibleSub / thermal / thermalSub` **手填的优先**（ONVIF 查不到、或厂家的配置文件划分不合常规时用），可以只填其中几路。
- ONVIF 查询失败、又没手填：该路不生成 source，`cam.online` 不计它；本地管理页「视频」页显示失败原因（连不上 / 认证失败 / 找不到热像源）与手填入口，诊断页出一条。
- **真机驱动 `restv1`（EG 0.5 起，清单 I18）**：流地址改用 `GET /restv1/channel/rtsp/:id`（通道 0 可见光、1 热像；主 / 子码流按返回的地址分），不依赖 ONVIF；手填仍优先。RTSP 端口固定 554。真机返回的地址**不带账号**（`rtsp://<摄像机>:554/<通道>/<main|sub>`），eg-video 拼上**取流账号**（`camera.user / password`）再给 mediamtx；restv1 接口用**接口账号**（`camera.restUser / restPassword`，留空 = 同取流账号）—— 真机这两套不是同一个（§10）。
- **编码**：四路都保持摄像机缺省的 **H.264**。可选的 H.265 不要开：浏览器（WHEP / HLS）大多播不了 H.265，子站也不转码。码率单位是 kbps；热像主码流 640×480。
- **会话数**：厂家答复最多 2 个会话同时连（CAM4）。EG 常拉两路子码流 + 按需拉主码流 + restv1 每秒轮询；「2 个会话」是否把 RTSP 拉流也算在内，**要在真机上确认**（如果算，调试时要先停 eg-video 再用厂家工具连）。

## 6. 抓帧（给 G5 告警抓拍用）

`POST http://127.0.0.1:9110/api/video/snapshot?ch=visible|ir` → `image/jpeg`（只听本机，agent 调）：

1. 真机驱动 `restv1`（EG 0.5 起）：`GET /restv1/channel/snap/:id`（0 可见光、1 热像），返回 JSON 里的 base64 JPG，解码后原样给（不经 mediamtx）；
2. 摄像机有 ONVIF `GetSnapshotUri` 就用它（不经 mediamtx，最快）；
3. 否则经本机 mediamtx 拉 `<柜号>` / `<柜号>-ir` 主码流解一帧（ffmpeg 单帧，J1900 上约 1 s；按需拉会顺带拉起、10 s 后自动断）。

回应头带 `X-Snapshot-Ts`（毫秒）与来源（`onvif` / `rtsp`）。失败回 503 + 原因。G5 由 agent 在告警事件发生时调，连同事件 id 上传子站。

## 10. 真机实测（2026-10-14，开发网）

样机接在开发网的 PoE 交换机上，开发机直连测（`cam-check` 脚本 + ffprobe；EG 侧 `pnpm restv1:probe`）。

**四路码流**（restv1 `channel/rtsp/0|1` 返回的地址；全部 H.264，与 §5 一致）：

| 路 | 地址 | 分辨率 | 帧率 |
|---|---|---|---|
| 可见光主码流 | `rtsp://<摄像机>:554/0/main` | 2560×1600 | 25 |
| 可见光子码流 | `rtsp://<摄像机>:554/0/sub` | 704×576 | 25 |
| 热像主码流 | `rtsp://<摄像机>:554/1/main` | 640×480 | 9 |
| 热像子码流 | `rtsp://<摄像机>:554/1/sub` | 640×480 | 9 |

- 热像主码流 640×480 与厂家 CAM5 一致；热像子码流与主码流同分辨率，只有 9 fps（热像机常见的 9 Hz 出口限制）。
- restv1 只有通道 0、1（`channel/rtsp/2` 回 404「Form … is not defined」）。

**账号**（口令不写进文档，见部署手册 §5a）：

- **restv1 接口与 RTSP 是两套账号**：接口（`/restv1/token`）用出厂的普通账号能登，但这个账号拉 RTSP 一律 401；RTSP 只认 `admin`（厂家答复），而 `admin` 登不了 restv1（`/restv1/token` 回 10001）。所以 EG 配置分开：`camera.user / password` = 取流账号（admin），`camera.restUser / restPassword` = 接口账号。
- RTSP 鉴权是标准 Digest（realm `LoginTo8000<序列号>`）：`uri` 写完整地址或只写路径都过；Basic、口令写 MD5 都不过。mediamtx / ffmpeg 用 URL 里的账号口令即可。
- 两个出厂口令投运前都要改（restv1 2.20「设置用户密码」能改 admin / 高级 / 普通三类账号）。

**网络与其它**：

- 出厂地址是 192.168.1.x 段的固定地址，不走 DHCP、不回 ONVIF 搜索（WS-Discovery 没回应）；开着 21 / 80 / 554 / 8000。接 EG 的 LAN1 时 LAN1 要配同网段地址，或先用 restv1 改摄像机地址。
- 出厂时钟是 1970 年：接 EG 前要配对时（restv1 有 NTP 参数），否则摄像机自己的 OSD 时间、报警时间都不对（EG 录像与告警用 EG 的钟，不受影响）。
- 开发网这台的交换机口只协商到 10M（PoE 约 3.3 W），可见光主码流 2560×1600 在 10M 上会不够；现场接线要确认百兆以上。
**EG 联调**（eg-video 用 restv1 驱动 + EG mediamtx，开发机直连样机；固件 `0000_B37_1.1.17`，型号 IRCAM）：

| 项 | 结果 |
|---|---|
| 流地址 / 探测 | restv1 查到 4 路；DESCRIBE 4 路都通（可见光 H264 25 fps、热像 H264 9 fps），`cam.online` = 4，`cam.vis / cam.ir / cam.rest` = OK |
| 拉流 | EG mediamtx 常拉两路子码流、按需拉两路主码流都通（admin 拼进地址，Digest） |
| 测温 | 每秒一次照常；全画面 max / min / avg / center 都有；12 个区出厂都停用，名字 `Area1`–`Area12`、类型 `rectangle` |
| 抓拍 | 可见光 2560×1600 约 500 KB，**3–3.9 s**；热像 640×480 约 70 KB，0.2–0.4 s；eg-video `/api/video/snapshot` 走摄像机抓拍（via=camera） |
| 会话数（G4-8） | 4 路 RTSP + 3 个 restv1 令牌同时在用，全部正常 —— 「最多 2 个会话」不含 RTSP，restv1 令牌这台也不止 2 个（多半指网页登录） |
| 报警状态 | 比文档多一项 `areaSecurity`（区域入侵）；每项带 `active`（布防）与 `alarm`（正在报警），驱动只看 `alarm` |

联调发现、已改驱动：

- 区域类型 `rectangle` → 按 `region`；出厂区域名 `Area<n>` 当没起名，按 ID 编 `R<n>`（ID 0 = R1）；`areaSecurity` → 「区域入侵」。
- **HTTP 接口串行**：可见光抓拍的 3–4 s 里测温请求排队，原来 3 s 超时会误报 TIMEOUT（温度标无效）—— 普通请求超时改 6 s；改后抓拍期间测温不再失败。
- **温度取到 0.1 ℃**（2026-10-15 各级前端联调）：真机回的温度是 float32 转出来的（35.150005、34.250008），原样送下去，子站监视墙、EG 本地页都显示成「34.250008℃」。驱动在源头把全画面与各区的 max / min / avg / center / pt 取到 0.1 ℃（`temp1`），与仿真器、agent 派生的温升 / 温差同一位数。
- RTSP 探测的认证重发改在同一条连接上发（摘要认证的常规做法；联调时 400 的直接原因其实是开发环境 `EG_CAM_HOST` 把探测指到了仿真摄像机，不是这台摄像机的问题）。

**G4-9：区域框 640×480、温度点 160×120**（已关闭）。

- 全画面：连续采样最高 / 最低温坐标，y 始终 ≤ 119、x ≤ 122；对着同一时刻的热像抓拍看，坐标乘 4 正好落在图上最热（左上）、最冷（右下）的位置。
- 区域：用 `POST /restv1/measurement/region/:id` 写两个矩形对照 —— 区 0 `(16,8,16×12)`、区 1 `(64,32,64×48)`（= 区 0 × 4）。读回的框坐标原样（框按写入的坐标存）；区 0 报的最高 / 最低点 (7,2) / (4,5)、区 1 报的 (24,13) / (31,10)，**各自乘 4 都落在自己的框里**（区 0：16–32 × 8–20；区 1：64–128 × 32–80），不乘就落在框外。所以框是 640×480、温度点是 160×120。
- 驱动：`RESTV1_POINT_SCALE = 4`，`maxX / maxY`（全画面与各区）乘 4 后再上报，`frame` 仍是 640×480 —— 子站 / 前端不用改，按 `frame` 换算即可。
- 测完两个区已恢复成停用（摄像机不接受 0×0 的框，留成 `(0,0,1×1)`、停用，与出厂等效）。
- 区域框坐标是 0×0 时写入回 10001：现场画区要给实际大小。
